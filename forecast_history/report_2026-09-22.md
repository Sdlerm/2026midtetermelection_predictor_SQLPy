Step 2 (pipeline run) failed immediately on the first script:

```
$ python senate_ingest.py
Traceback (most recent call last):
  File "senate_ingest.py", line 315, in <module>
    con.commit()
sqlite3.OperationalError: disk I/O error
```

Diagnosis: this is an environment problem, not a data or model problem. The connected project folder used by this run does not allow files to be deleted once written (confirmed separately: a plain `rm` on a test file in `db/` returned "Operation not permitted"). SQLite's default rollback-journal mode needs to delete the `elections.db-journal` file after every successful commit, and that delete is being blocked — which surfaced as a "disk I/O error" on commit. A stale 70KB `elections.db-journal` was left behind from the failed attempt, and afterward even a read-only `PRAGMA` query against the live database failed the same way, because SQLite tries to roll back that hot journal on open.

I copied `elections.db` to a scratch location and ran `PRAGMA integrity_check` against the copy: it came back clean (`ok`), and the poll data read back correctly (3,640 rows, max date 2026-09-21). **The database itself is not corrupted** — this is specific to how this automated run's sandbox is mounting the project folder, not damage to your data.

I stopped here rather than attempting a fix (e.g., forcing WAL journal mode, or manually clearing the stale `-journal` file) since that touches database internals and this task's instructions are to report failures rather than patch around them.
